# From power to C

BootPI targets the Raspberry Pi 4 Model B's standard firmware path. It supplies
the ARM executable, not replacements for the ROM, EEPROM loader, or VideoCore
firmware.

```text
VideoCore: BCM2711 ROM -> SPI EEPROM loader -> start4.elf
ARM:       built-in 64-bit stub -> _start -> kernel_main
```

On power-up, the VideoCore subsystem executes the BCM2711 boot ROM while the
ARM application has not started. The ROM normally loads the second-stage
loader from SPI EEPROM; recovery paths also exist. The EEPROM loader discovers
boot media using its configured `BOOT_ORDER`, performs early hardware setup,
and loads the VideoCore firmware from a bootable FAT partition. For Pi 4 this
is normally `start4.elf`, with its matching `fixup4.dat`. This replaces the
older boards' SD-card `bootcode.bin` stage. See the official
[EEPROM boot flow](https://www.raspberrypi.com/documentation/computers/raspberry-pi.html#eeprom-boot-flow)
and [boot files](https://www.raspberrypi.com/documentation/computers/configuration.html#boot-folder-contents).

The firmware reads `config.txt`, loads the selected ARM image into RAM, and
prepares the ARM stub and supporting data. Starting the Cortex-A72 cores
executes that stub on ARM; the preceding loaders and firmware execute on the
VideoCore side. The stub initializes platform state and branches to the image
entry. BootPI's first image bytes are `_start`. The firmware does not parse our
ELF symbol table: it loads the raw `kernel8.img` bytes generated by the build.
The [official configuration reference](https://www.raspberrypi.com/documentation/computers/config_txt.html#boot-options)
documents kernel selection and the built-in stub.

## Address and entry contract

`config.txt` selects AArch64 with `arm_64bit=1` and explicitly names
`kernel8.img`. It also sets `kernel_address=0x80000`, matching `linker.ld`.
Although `0x80000` is widely used by older bare-metal examples, the current
[official address reference](https://www.raspberrypi.com/documentation/computers/legacy_config_txt.html#kernel_address)
lists `0x200000` as the 64-bit default. The explicit setting avoids depending
on that default. Do not enable `kernel_old`, which selects address zero.
`arm_peri_high=0` requests the low ARM peripheral mapping used by the GPIO
driver. These settings are scoped to `[pi4]` and are not a Pi 5 configuration.

BootPI relies on the default 64-bit stub, with no custom `armstub` file. The
published Raspberry Pi [stub source at tools commit
439b6198](https://github.com/raspberrypi/tools/blob/439b6198a9b340de5998dd14a26a0d9d38a6bcac/armstubs/armstub8.S)
establishes nonsecure EL2h, little-endian execution, masked D/A/I/F, and an
`SCTLR_EL2` configuration with the MMU and instruction/data caches disabled.
It initializes the generic counter frequency metadata. Core 0 branches to the
firmware-provided kernel entry; the other cores remain in its spin-table loop
unless released. BootPI never releases them.

The stub passes a device-tree pointer in `x0` and clears `x1` through `x3`.
BootPI does not consume those arguments or depend on other general-register
values. It establishes its own stack and BSS contents. This is a documented
supported configuration, not a promise about arbitrary custom stubs or firmware
versions. The application stays at EL2, so an exception-level transition is
unnecessary.

## What `_start` provides

Startup masks interrupts before C code runs, reads `MPIDR_EL1` to identify core
0, and parks any secondary core that reaches this image. It also checks
`CurrentEL` and parks unless entry is at EL2. Its `wfe` loop always
branches back, so an event cannot accidentally enter the kernel. Selecting the
current level's stack and loading `__stack_top` establishes the 16-byte alignment
required by the AArch64 C calling convention.

The linker marks BSS as `NOLOAD`: no zero-filled payload is copied from the
card. Assembly clears `__bss_start` through `__bss_end` before C uses static
storage. Initialized data already occupies its linked RAM address in the raw
image, so it needs no separate ROM-to-RAM copy. The reserved stack follows the
image and BSS without overlap. Startup calls `kernel_main`; if C returns, it
falls into the same safe parking loop. There is no C runtime, allocator, or
exception handler. See [the memory layout](memory-map.md).

At EL2 the physical generic counter is accessible without enabling EL1 or EL0
access. The timer module reads `CNTPCT_EL0` and firmware-populated
`CNTFRQ_EL0`; it does not program interrupts. An `isb` before a count read
prevents speculative instruction ordering from moving that observation ahead
of preceding instructions. Reading the frequency register avoids a clock-rate
constant in the application. See Arm's [Generic Timer guide, count/frequency
section](https://documentation-service.arm.com/static/6294c39db334256d9ea8ae53?token=).

## Terms used here

A **core** is a hardware execution engine; the BCM2711 has four Cortex-A72
cores. **Firmware** is platform software that initializes or manages hardware.
A **bootloader** is software whose role is to prepare and start the next
program. **Kernel** names this project's privileged bare-metal entry program;
it is not a complete operating system. A **thread** is a schedulable execution
context, and a **process** is an operating-system resource and address-space
container. BootPI creates neither threads nor Linux-style processes: core 0
simply executes one program.

Building and inspecting the image establishes its static layout and instruction
flow. Only a physical Pi 4 can establish that this firmware path reaches our
code and that the LED actually blinks.
