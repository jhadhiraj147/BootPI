# BootPI

BootPI boots a Raspberry Pi 4 Model B directly into a small AArch64 bare-metal
program and blinks an external LED on GPIO17. It demonstrates startup assembly,
the C memory layout, memory-mapped register access and the ARM generic counter.
It runs on one Cortex-A72 core without Linux or a C runtime.

## Build

On Arch Linux, the required packages are `clang`, `lld`, `llvm`, `make` and
`python`. Git is needed to clone the repository; `curl` is used by the firmware
download recipe. Clang cross-compiles to `aarch64-none-elf`, so a separate GCC
cross-toolchain is unnecessary.

```sh
make             # kernel8.img and build/kernel8.elf
make check       # host logic tests and static ELF/image checks
make inspect     # ELF headers, sections and symbols
make disasm      # display instructions; also writes build/kernel8.dis
make clean
```

The build uses Cortex-A72 instructions, freestanding C11, general registers
only, warnings as errors and a custom linker script. No libc, startup library
or compiler runtime is linked. Source/header and Makefile changes trigger
incremental rebuilds. When overriding compiler flags or tool variables on the
command line, run `make clean` first. Tool variables such as `CC`, `LD` and
`OBJCOPY` can be overridden with Make arguments.

## Boot and memory

```text
VideoCore ROM -> SPI EEPROM loader -> VideoCore firmware
    -> ARM 64-bit stub -> _start -> kernel_main -> GPIO17 blink loop
```

`config.txt` selects 64-bit execution, `kernel8.img`, the low peripheral mapping
and an explicit physical load address of `0x80000`, matching `linker.ld`.
The standard firmware stub enters nonsecure EL2 with MMU/caches disabled.
Startup masks interrupts, checks the core and exception level, sets a 16-byte
aligned stack, clears BSS and calls C. Secondary cores remain parked. Loaded
initialized data is already at its linked RAM address.

The explicit load address avoids depending on firmware defaults. The
[boot-process notes](docs/boot-process.md) describe each stage, the supported
entry contract, and the distinction between the VideoCore and ARM programs,
with links to official Raspberry Pi and Arm sources.

## Run on the board

Use a Pi 4 Model B (BCM2711), a microSD card with a FAT32 boot partition and a
suitable power supply. Put these files at the partition root:

```text
config.txt                  # from this repository
kernel8.img                 # generated by make
start4.elf                  # external Raspberry Pi firmware
fixup4.dat                  # matching firmware fixups
bcm2711-rpi-4-b.dtb          # external Pi 4 Model B device tree
```

Firmware is not bundled. The [hardware setup guide](docs/hardware-setup.md)
provides a pinned firmware download and copy recipe, including its licence
notice. No SD-card `bootcode.bin`, custom ARM stub or Linux root filesystem is
needed for this configuration. Unmount the card before inserting it into the
Pi.

Disconnect power and wire:

```text
GPIO17, physical pin 11 -> 330 ohm resistor -> LED anode (+)
LED cathode (-) -> GND, physical pin 6
```

Use a red LED and a common ground. Always use the current-limiting resistor;
GPIO is 3.3 V and must never be driven with 5 V. Expected behavior is 500 ms on,
500 ms off continuously, with small polling overhead. Physical testing is
still required.

## Registers and timing

The CPU executes ordinary loads/stores at peripheral addresses. The interconnect
routes them to the GPIO controller, which drives the physical pin. GPIO starts
at ARM physical address `0xfe200000`. The driver preserves neighboring
function-select fields and uses write-one SET/CLR registers. `volatile`
preserves compiler-visible accesses; it does not supply all hardware ordering
guarantees. The [memory-map notes](docs/memory-map.md) explain the registers,
address spaces and barriers.

The first blink used an uncalibrated counted loop. It now reads the physical
counter (`CNTPCT_EL0`) and firmware-provided frequency (`CNTFRQ_EL0`) at EL2.
Milliseconds round up to ticks, and 56-bit modular elapsed arithmetic handles
counter wrap. A completion barrier puts GPIO writes before the timing baseline;
an instruction barrier orders each counter read. This is a polling busy wait,
with no timer interrupts. Missing frequency metadata leaves the LED low.

## Source layout

- `boot/start.S`, `linker.ld`: entry, core parking, C setup and memory layout.
- `src/kernel.c`: LED application; `src/gpio.c`: bank-0 output driver.
- `src/timer.c`, `src/timer_math.h`: counter access and delay arithmetic.
- `include/`: GPIO, MMIO and timer interfaces.
- `tests/`: GPIO host tests, timer arithmetic tests and a linker-layout fixture.
- `scripts/check_elf.py`: standard-library-only ELF/image validation.
- `docs/`: boot process, memory map and hardware setup.

Generated artifacts under `build/` and `kernel8.img` are ignored by Git.

## Verification and limits

Host validation on Arch Linux with Clang 23.1.3 and LLD 23.1.4 passed:

- Warning-free AArch64 build; ELF entry `_start` at `0x80000`.
- Static sections and load segments, aligned BSS/stack, and raw image bytes.
- No unresolved symbols, dynamic linking, relocations or runtime dependencies.
- GPIO register addresses, function masks, SET/CLR semantics and invalid pins.
- Delay conversion extremes, rounding and counter wrap arithmetic.
- Initialized data/read-only data/odd-sized BSS through a separate fixture.

Startup and counter instructions were reviewed in disassembly. Two clean
parallel builds produced identical ELF and image bytes with this toolchain;
header/Makefile dependency propagation and an unchanged incremental build were
checked. The image checker also rejected a corrupted byte and mismatched
firmware load address.

**No physical Pi boot or LED blink has been tested.** Firmware handoff, actual
GPIO output and observed timing remain to be verified on the board. There is
no exception handling, console, allocator, scheduler or virtual memory. This
is a small boot and GPIO foundation, not a complete operating system.
